# Contract Upgrade Guide (v0 -> v1)This guide documents the upgrade procedure from account contract 0 (current) to 1 (with session key policy scoping), including on-chain storage migration, SDK compatibility, and rollback plans.## Problem StatementThe contract's upgrade() function replaces the WASM logic but does not automatically migrate the storage layout. When new fields (like llowed_contracts) are added to the SessionKey struct in 1, any existing stored session keys (from 0) will be missing these fields. Attempting to deserialize them using the new struct definition will cause panics.## Storage Schema Changes### v0 SessionKey (Old)`ust#[contracttype]pub struct SessionKeyV0 {    pub public_key: BytesN<32>,    pub expires_at: u64,    pub permissions: Vec<u32>,}`### v1 SessionKey (New)`ust#[contracttype]pub struct SessionKey {    pub public_key: BytesN<32>,    pub expires_at: u64,    pub permissions: Vec<u32>,    pub allowed_contracts: Option<Vec<Address>>, // <-- NEW FIELD}`## Migration Entry PointA new migrate(env: Env, old_version: u32, session_keys: Vec<BytesN<32>>) function has been added.It reads the old SessionKeyV0 structs for the provided public keys, adds the default None for llowed_contracts, and rewrites them as 1 SessionKey structs.## Safe Upgrade SequenceTo prevent a window where the new WASM is active but storage is not migrated, perform the upgrade and migration within the same transaction:1. **Upload** the new WASM and obtain its hash.2. Build a single transaction containing:   - Call upgrade(new_wasm_hash)   - Call migrate(0, session_keys) (pass all existing session public keys)3. **Submit** the transaction.By bundling both calls in one transaction, the contract atomically upgrades its logic and migrates its state.## SDK Version Compatibility- **Ancore SDK v0.x**: Compatible with 0 contract.- **Ancore SDK v1.x**: Compatible with 1 contract. Will expect the llowed_contracts field during session key generation and retrieval.## Rollback PlanIf an emergency revert is needed:1. Use the 0 WASM hash to perform an upgrade(v0_hash).2. Since 0 does not know about the llowed_contracts field, returning to 0 might result in deserialization issues if 0 SDK cannot ignore the extra fields in storage. In such a scenario, session keys should be revoked and recreated under the 0 logic. Ensure the 0 WASM hash is securely documented before upgrading.
